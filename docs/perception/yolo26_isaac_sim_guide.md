# YOLO26 인지 파이프라인 가이드 (Isaac Sim → Jetson Orin Nano)

Isaac Sim에서 합성 데이터를 만들어 YOLO26을 학습하고, Jetson Orin Nano에서 TensorRT로 실행하기까지의 가이드.

- 학습: 개발 PC (RTX 5060 Laptop 8GB)
- 실행: Jetson Orin Nano (SLAM, Nav2와 GPU/메모리 공유)
- 카메라: Arducam UC-684 (상단 광각), RealSense D435 (손목)
- 대상: QR(JSON), 퍽 (원기둥 Ø3×6cm / 사각기둥 3×3×6cm, 색 R/G/B 중 무작위, 무광), 신호등, 칸이 나뉜 적재함

> `[확인 필요]` 표시는 아직 정해지지 않은 값이다. 정해지면 이 문서를 갱신한다.

## 0. 핵심 결정 요약

| 항목 | 결정 |
|---|---|
| 모델 | `yolo26n` detection **하나**를 두 카메라에 공용으로 사용. 가중치는 같고 엔진만 카메라별로 2개 |
| 입력 크기 | **실제 캡처 해상도 기준**. 광각 1280×720 캡처 → 엔진 `736×1280`, D435 640×480 → `480×640` |
| 손목 마스크 | seg 대신 bbox + depth 전경 분리로 얻음. 맞닿은 퍽에서 실패할 때만 seg 추가 |
| 퍽 색 | YOLO 클래스로 나누지 않음. 마스크·bbox 내부 HSV로 판별하고 카메라별로 따로 보정 |
| QR | YOLO는 위치만 찾고, 내용은 손목 카메라 + 디코더(zxing-cpp / pyzbar)로 읽음 |
| 적재함 | 칸별 재고 상태를 기록하고, 손목 고정 자세 + 칸별 ROI로 확인 (YOLO는 보조) |
| 경량화 | TensorRT FP16이 기본. INT8 PTQ는 실험해 보고 정확도 손실이 작을 때만 채택 |
| sim-to-real | 실제 카메라 보정값을 sim에 반영, 도메인 랜덤화, 실제 데이터 소량 fine-tune, 실제 데이터 검증셋으로만 판단 |

## 1. 카메라 역할 분배

나누는 기준은 **작업 종류가 아니라 거리와 단계**다. 광각은 넓게 찾고 결과를 확인하며, 손목은 가까이에서 정밀하게 읽고 잡는다.

| 단계 | 광각 (상단) | RealSense (손목) |
|---|---|---|
| 주행 탐색 | QR·퍽·신호등 탐지 (상시) | (전방 주시 자세일 때) 신호등 보조 |
| QR | 벽에서 QR 위치 탐지 | 정면 정렬 후 디코딩 → JSON |
| 퍽 원거리 | 탐지 + 색 → homography로 바닥 좌표 | – |
| 퍽 근거리 / 집기 | – | 탐지 + depth 마스크로 색 재확인, 잡을 지점 계산 |
| 적재함 넣기·꺼내기 | 일부만 보여서 사용하지 않음 | 고정 자세로 칸별 확인 |
| 밀기·넘어뜨리기 | 퍽과 목표를 동시에 추적, 결과 확인 | 접근 직전 위치 보정 |

### 상태 머신

```
EXPLORE  : Nav2 주행 + 광각 YOLO 상시 실행 (10~15Hz)
  ↓ qr 발견
APPROACH : bbox 방향 + 라이다로 벽 앞 약 0.4m 지점까지 이동
AIM      : 팔을 QR 정면으로 → DECODE (여러 프레임 결과 일치 시 확정, JSON 스키마 검증)
  ↓ {target, color, action}
SEARCH   : 광각으로 해당 색 퍽 찾기 → 바닥 좌표
ALIGN    : 손목 YOLO + depth로 3D 위치 보정
EXECUTE  : 집기 → 적재함 / 밀기 / 넘어뜨리기
VERIFY   : 광각으로 결과 확인. 실패하면 ALIGN부터 재시도
```

### 광각 카메라 장착

완전히 바로 아래를 보게 달면 벽의 QR과 신호등이 보이지 않는다. **앞쪽 아래로 30~45° 기울여서** 화면 아래쪽은 바닥과 퍽, 위쪽은 벽과 전방이 보이게 한다. `[확인 필요: 장착 높이·각도]`

## 2. 클래스 정의

| id | 클래스 | 카메라 | 비고 |
|---|---|---|---|
| 0 | `qr` | 광각, 손목 | 위치만 찾는 용도. 디코딩은 별도 |
| 1 | `puck` | 광각, 손목 | 서 있는 퍽 (원기둥·사각기둥 모두). 색은 후처리로 판별 |
| 2 | `puck_fallen` | 광각, 손목 | 넘어진 퍽. VERIFY 단계에서 필요 |
| 3 | `signal_tower` | 광각 | 적층 신호등(타워램프) 전체. 어느 칸이 켜졌는지는 후처리로 판별 |
**벽 연결 부품은 클래스로 두지 않는다.** 미로 벽 연결 부품(3D 프린팅, 높이 39cm 기둥 + 지름 6cm 캡)은 파란 퍽과 색이 같다. 그래도 라벨 없이 두면 YOLO가 배경으로 학습하므로, 학습 이미지에 연결 부품이 충분히 들어 있으면 퍽과 구분하게 된다 (hard negative). 우리 데이터는 sim·실제 모두 장면마다 연결 부품이 많이 찍히므로 충분하다. 클래스로 두면 실제 영상에서 한 장에 10개 이상씩 라벨링해야 해서 비용 대비 이득이 작다.
- sim에서는 `wall_joint` 라벨을 남겨 두고 **오탐 평가용**으로만 쓴다 (퍽 탐지가 연결 부품 bbox와 겹치는 비율).
- 오탐이 줄지 않으면 `convert_to_yolo.py --with-joint`로 클래스에 넣어 다시 학습한다.

**퍽 색을 클래스로 두지 않는 이유**: 색은 sim과 실제의 차이가 가장 큰 속성이다. 클래스로 두면 현장 조명이 바뀔 때마다 재학습해야 하지만, 후처리로 두면 임계값만 다시 보정하면 된다. 또 학습 때 `hsv_h` 증강을 크게 줘서 탐지기가 색에 둔감해지도록 만들 수 있다.

**신호등 상태를 클래스로 두지 않는 이유**: 신호등은 위에서부터 회색 캡, 빨강, 노랑, 초록이 쌓인 원통형 타워램프다. 렌즈 자체가 색이 있는 반투명 플라스틱이라 **꺼져 있어도 세 색이 모두 보인다.** 그래서 상태는 색이 아니라 **칸별 밝기**로 구분해야 한다. 칸의 위치는 고정되어 있으므로 bbox를 세로로 나눠 밝기를 비교하는 편이 클래스 3개로 학습하는 것보다 확실하고, sim-to-real 차이에도 덜 민감하다.

### 신호등 점등 판별 (후처리)

```python
# bbox를 실측 비율로 세로 분할 (위→아래: 캡, R, Y, G). 비율은 실측 후 config에 저장
TIERS = {"red": (0.10, 0.40), "yellow": (0.40, 0.70), "green": (0.70, 1.00)}   # 실측 비율. 실제 카메라 bbox로 재보정
v = cv2.cvtColor(roi, cv2.COLOR_BGR2HSV)[..., 2]
cx0, cx1 = int(w * 0.25), int(w * 0.75)                 # 가장자리 반사를 피해 가운데 폭만 사용
score = {k: np.percentile(v[int(a*h):int(b*h), cx0:cx1], 90) for k, (a, b) in TIERS.items()}
lit = max(score, key=score.get)
others = sorted(score.values())[:-1]
state = lit if score[lit] - max(others) > V_MARGIN else "off"   # 차이가 작으면 꺼짐 또는 판단 불가
```

- 여러 프레임 중 다수결로 확정한다 (깜빡임 모드가 있으면 확정 구간을 늘림).

### 퍽 색 판별 (후처리)

```python
# 마스크(손목) 또는 bbox 중앙 60% 영역(광각) 픽셀만 사용
hsv = cv2.cvtColor(roi, cv2.COLOR_BGR2HSV)
px = hsv[mask > 0]
px = px[(px[:, 1] > S_MIN) & (px[:, 2] > V_MIN)]   # 채도·밝기가 낮은 픽셀(그림자, 모서리) 제외
h = np.median(px[:, 0])                            # OpenCV hue 범위: 0~179
# R: h<10 or h>170, G: 40~85, B: 95~130  ← 카메라별로 실측해서 config에 저장
```

- 두 카메라 모두 **auto exposure와 auto white balance를 끄고 고정**한다 (2.1절).
- 임계값은 `config/color_<camera>.yaml`에 카메라별로 저장하고, 시연장 조명에서 다시 보정한다.

### 2.1 카메라 노출·화이트밸런스 고정

카메라는 기본적으로 장면에 맞춰 밝기(auto exposure)와 색감(auto white balance)을 계속 자동 조정한다. 이 상태로 두면 다음 문제가 생긴다.

- 켜진 신호등이 화면에 들어오면 카메라가 화면 전체를 어둡게 조정해서 퍽 색이 달라진다.
- 바닥이나 벽 색이 화면을 많이 차지하면 화이트밸런스가 틀어져서 퍽 hue가 이동하고, 색 임계값이 맞지 않게 된다.
- Isaac Sim 카메라에는 이런 자동 조정이 없으므로 그 자체가 sim-to-real 차이가 된다.

그래서 두 카메라 모두 수동 값으로 고정한다.

```bash
# Arducam (UVC): 지원하는 컨트롤 이름부터 확인 (커널마다 이름이 다름)
v4l2-ctl -d /dev/video0 --list-ctrls
v4l2-ctl -d /dev/video0 -c auto_exposure=1 -c exposure_time_absolute=150 \
  -c white_balance_automatic=0 -c white_balance_temperature=4600 -c gain=0
```

```yaml
# RealSense (realsense-ros 파라미터)
rgb_camera.enable_auto_exposure: false
rgb_camera.exposure: 150
rgb_camera.gain: 64
rgb_camera.enable_auto_white_balance: false
rgb_camera.white_balance: 4600.0
```

**값 정하는 법**: 시연장과 비슷한 조명에서 신호등을 켜고 퍽과 같이 화면에 넣은 다음,
1. 켜진 칸이 하얗게 날아가지 않고 색이 남아 있으며,
2. 꺼진 칸과 밝기 차이가 확실하고,
3. 퍽이 너무 어둡지 않은

노출을 찾는다. 주행 중 모션 블러가 생기면 노출 시간을 줄이고 gain을 올린다. 확정한 값은 `config/camera_<name>.yaml`에 저장하고 시연장에서 한 번 더 조정한다.

## 3. 모델 선택과 입력 크기

### 3.1 모델 하나를 공용으로 사용

`yolo26n` detection 모델 하나를 두 카메라에 쓴다. 학습 데이터에 광각 시점과 손목 시점을 모두 넣고(4.3절), 가중치는 같게 둔 채 **입력 크기만 다른 TensorRT 엔진 2개**를 만든다.

| 엔진 | 카메라 | 실행 시점 |
|---|---|---|
| `wide_736x1280.engine` | 광각 | 상시 (10~15Hz) |
| `wrist_480x640.engine` | D435 컬러 | ALIGN·EXECUTE·적재함·QR 단계에서만 |

- 두 엔진을 **한 프로세스에서** 불러온다. 프로세스를 나누면 CUDA context가 프로세스마다 수백 MB씩 생겨서, SLAM·Nav2와 8GB를 나눠 쓰는 Orin Nano에 부담이 된다.
- 두 엔진이 동시에 계속 돌지 않게 상태 머신으로 켜고 끈다. Orin Nano에는 DLA가 없으므로 모든 연산을 GPU 하나에서 처리한다.
- 라벨 변환, 학습, INT8 실험을 모두 한 벌로 끝낼 수 있다.

### 3.2 손목 마스크는 depth로 얻음 (seg 미사용)

퍽은 바닥이나 적재함 바닥 위에 있는 3×3×6cm 크기의 원기둥 또는 사각기둥이다. 그래서 bbox 안에서 배경보다 가까운 depth 픽셀만 남기면 마스크가 된다.

```python
# D435는 depth를 color에 정렬(align)해서 사용
d = depth[y0:y1, x0:x1].astype(np.float32)
valid = d > 0
bg = np.percentile(d[valid], 90)                 # bbox 안의 바닥/배경 깊이
mask = valid & (d < bg - 0.015)                  # 배경보다 1.5cm 이상 가까운 픽셀 = 퍽
pts = deproject(mask, d, K)                      # 마스크 픽셀 → 3D 점군
center, axis = pts.mean(0), pca_main_axis(pts)   # 축이 수직이면 서 있음, 수평이면 넘어짐
```

- 색 판별은 이 마스크 안쪽 픽셀로만 한다.
- 적재함은 칸별 ROI로 처리한다(8절).
- **사각기둥은 잡는 방향이 정해져 있다.** 서 있는 사각기둥은 점군을 위에서 본 윤곽(`cv2.minAreaRect`)으로 면 방향(yaw)을 구하고, 그리퍼를 면과 평행하게 맞춘다. 원기둥은 방향과 관계없이 잡을 수 있다. 위에서 본 윤곽이 원인지 사각형인지로 두 모양을 구분할 수도 있다.
- **seg를 추가하는 조건**: 퍽 여러 개가 맞닿아 있어서 depth로 분리되지 않는 실패가 실제로 반복될 때만 `yolo26n-seg`로 바꾼다.

### 3.3 입력 크기는 실제 캡처 해상도 기준

입력 크기는 아래 순서로 정한다.

1. **실제 캡처 모드를 먼저 확정한다.** USB 대역폭과 FPS를 고려해 실제로 받을 해상도를 정한다. `[확인 필요: UC-684 캡처 모드]`
2. **Isaac Sim 렌더 해상도와 intrinsics를 그 캡처 모드에 정확히 맞춘다.** 해상도가 다르면 객체 크기 분포가 달라져서 그 자체가 sim-to-real 차이가 된다.
3. **엔진 입력 크기는 캡처 해상도 이하로, 비율도 맞춘다.** 캡처보다 크게 잡으면 업샘플링일 뿐 정보가 늘지 않는다. 16:9 영상에 정사각형 입력을 쓰면 패딩만큼 연산이 낭비된다. 크기는 32의 배수여야 한다.

| 카메라 | 캡처 (예시) | 엔진 입력 (h×w) |
|---|---|---|
| 광각 | 1280×720 | 736×1280 (원본 그대로) |
| 광각 (연산 부족 시) | 1280×720 | 544×960 |
| D435 컬러 | 640×480 | 480×640 |

학습은 mosaic 증강 때문에 정사각형(`imgsz`=긴 변)으로 하고, export할 때 직사각형 크기를 지정한다(5·6절).

### 3.4 광각에서 작은 퍽

실측 캘리브레이션 값([`camera_calibration.md`](camera_calibration.md), 수평 화각 약 94°, fisheye fx ≈ 853)으로 계산한, 퍽(지름 3cm)이 **엔진 입력에서** 차지하는 가로 픽셀 수다. fisheye라서 같은 거리라도 화면 가운데가 가장 크고 가장자리로 갈수록 작다.

| 거리 | 화면 중앙 | 광축에서 30° | 가장자리 근처 (45°) | 입력 폭 960, 가장자리 |
|---|---|---|---|---|
| 0.8m | 약 32px | 약 29px | 약 24px | 약 18px |
| 1.2m | 약 21px | 약 19px | 약 16px | 약 12px |
| 1.8m | 약 14px | 약 13px | 약 11px | 약 8px |
| 2.5m | 약 10px | 약 9px | 약 8px | 약 6px |

계산: 픽셀 수 ≈ fx × dθd/dθ × 0.03 / 거리 (θd는 OpenCV fisheye 왜곡 다항식). 입력 폭 1280 기준이며, 960 열은 0.75배.

> 이전 판은 수평 FOV 120° pinhole을 가정해 1.2m에서 약 9px로 계산했다. 실측값으로는 약 2배 크게 보인다.

YOLO가 안정적으로 잡으려면 대략 8~10px 이상이 필요하다.

1. 입력 1280이면 **1.8m까지는 화면 어디에 있어도 10px 이상**이다. 유효 탐지 거리는 1.8m 안팎으로 잡고, 그보다 먼 퍽은 다가가서 다시 본다. 실제 영상(`val_real`)의 퍽 recall로 최종 확정한다.
2. 연산이 부족해 입력을 960(544×960)으로 줄여도 1.2m까지는 가장자리에서 12px 이상이라 여유가 있다.
3. 모델 크기(s, m)를 키우기보다 캡처 해상도를 줄이지 않고 그대로 넣는 편이 효과가 크다.
4. 카메라가 바닥에서 614mm 높이에 앞쪽 아래로 기울여 달리므로, 실제로 보이는 바닥 범위는 거리보다 **기울기**가 정한다. 장착 후 기울기를 측정(11.4)해서 다시 확인한다.
5. 천장처럼 쓸모없는 영역은 잘라내고(ROI crop) 바닥과 벽 영역만 넣는다. 잘라낸 크기에 맞춰 엔진 입력도 줄인다.
6. YOLO26의 STAL(작은 객체를 고려한 라벨 할당)이 작은 물체에 유리하다.

### 4.2 카메라를 실물과 일치시키기 (sim-to-real에서 가장 중요)

1. 실제 카메라 두 대를 먼저 캘리브레이션한다. 광각은 OpenCV fisheye 모델, D435는 공장 intrinsics를 쓴다.
2. 그 intrinsics와 왜곡 계수를 Isaac Sim 카메라에 그대로 넣는다. 광각은 fisheye(OpenCV fisheye 렌즈 모델) 카메라로 만든다.
3. 해상도와 장착 위치(URDF 기준 TF)도 실물과 같게 한다.
4. YOLO는 **왜곡된 원본 영상에서 그대로** 돌린다. homography를 계산할 때만 bbox 좌표를 undistort한다.

### 4.3 시점별 데이터 비율

| 시점 | 비율 | 생성 방법 |
|---|---|---|
| 광각 주행 시점 | 50% | 로봇 위치와 방향을 맵 안에서 무작위로 바꾸고, 카메라는 로봇에 고정 |
| 손목 접근·집기 시점 | 25% | 퍽 주변 반구 위에서 카메라 위치를 무작위로 잡고(거리 0.15~0.5m), 퍽을 바라보게 함 |
| 손목 적재함 시점 | 10% | 고정된 적재함 확인 자세 ± 작은 흔들림 |
| 손목 QR 시점 | 15% | QR 정면 ± 30°, 거리 0.25~0.8m |

시작 규모는 8,000~10,000장이다. 실제 영상과 비교해서 부족한 시점을 보충해 나간다.

### 4.4 도메인 랜덤화 항목

| 항목 | 범위 |
|---|---|
| 조명 | 개수 1~4, 세기 ±50%, 색온도 3000~6500K, 위치 |
| 퍽 색 | **실측한 R/G/B 값 주변으로만** ±(H 5, S 15%, V 20%). 아예 무작위 색은 쓰지 않음 |
| 퍽 재질 | 무광: roughness 0.6~0.9 |
| 바닥·벽 텍스처 | 실제 촬영본 + 비슷한 계열 텍스처 |

### 4.5 생성 스크립트 (`yolo/dataset_gen/`)

> 기준 환경: **Isaac Sim 6.2 (pip 설치, Ubuntu 24.04, venv `~/env_isaacsim62`)**. API 이름은 버전마다 조금씩 다르므로 다른 버전이면 해당 문서를 확인할 것.
>
> **VRAM 8GB 주의** (권장 16GB): 장면을 단순하게 유지하고, path tracing 대신 실시간 RTX 모드를 쓰고, `rt_subframes`를 4~8로 둔다. 데이터 생성 중에는 YOLO 학습을 같이 돌리지 않는다 (VRAM 부족).

| 파일 | 역할 | 실행 환경 |
|---|---|---|
| `assets.py` | 퍽(원기둥·사각기둥), 신호등(STL040 3단) USD 생성, 색·점등 상태 설정 | Isaac Sim venv |
| `maze.py` | 미로 STL 로딩, 이동 가능 영역·벽 구간·시야 가림 계산. 단독 실행하면 확인용 그림 저장 | 아무 python (cv2, numpy) |
| `generate.py` | 장면 구성 + 랜덤화 + BasicWriter 저장. `--camera wide` / `wrist` | Isaac Sim venv |
| `viz_labels.py` | bbox와 정답(퍽 색, 신호등 상태)을 그려서 확인 | 아무 python (cv2, numpy) |
| `convert_to_yolo.py` | YOLO 형식으로 변환, `data.yaml` 생성 | 아무 python (numpy) |

**생성** (ROS 경로가 섞이지 않게 `PYTHONPATH`를 비우고 실행):

```bash
env -u PYTHONPATH ~/env_isaacsim62/bin/python yolo/dataset_gen/generate.py \
  --camera wide --frames 500 --seed 0 --out yolo/datasets/sim_raw/wide_000
env -u PYTHONPATH ~/env_isaacsim62/bin/python yolo/dataset_gen/generate.py \
  --camera wrist --frames 250 --seed 0 --out yolo/datasets/sim_raw/wrist_000
```

- 이 PC 기준 약 **초당 1~2장**이 생성된다 (시작 약 10초 + `rt_subframes=8`).
- 카메라는 실제 맵의 이동 가능 영역(벽에서 15cm 이상)에만 놓이고, 매 장면 선반 하나를 주 대상으로 삼아 그쪽을 바라본다. 벽에 가려 선반이 안 보이는 위치는 제외한다.
- 실행마다 `--seed`와 `--out`을 다르게 준다. 같은 seed는 같은 장면을 만든다.
- 출력 폴더에는 BasicWriter 파일(`rgb_*.png`, `bounding_box_2d_tight_*`)과 함께 `meta_*.json`이 저장된다. 퍽 색과 신호등 상태의 정답이 들어 있어서, 색 판별·점등 판별 후처리를 sim 데이터로 먼저 검증할 수 있다.
- `--seg`를 주면 instance segmentation도 저장한다 (seg 모델이 필요해질 때).
- `yolo/datasets/`는 `.gitignore`에 들어 있다.

**확인**:

```bash
python3 yolo/dataset_gen/viz_labels.py yolo/datasets/sim_raw/wide_000    # → wide_000/viz/viz_XXXX.png
```

**현재 장면에서 임시값인 것** (실측 후 `generate.py`의 `CAMERA_PROFILES`, `assets.py` 상단 상수를 교체):

| 항목 | 현재 값 | 교체 시점 |
|---|---|---|
| 광각 카메라 | pinhole, 1280×720, HFOV 100°, 높이 0.35~0.55m, 아래로 25~50° | 11.1, 11.3, 11.4 측정 후. fisheye 모델로 교체 |
| 손목 카메라 | pinhole, 640×480, HFOV 69° | D435 `camera_info` 확인 후 |
| 퍽 색 | R/G/B 기준 HSV 주변 ±(H 0.015, S 15%, V 20%) | 11.9 색 측정 후 |

| 선반 | 높이 7.5~8.5cm, 길이 15~30cm, 깊이 7~15cm, 벽 구간에 1~4개 무작위 | 선반 위치·크기 확인 후 |

| QR | 아직 없음 | JSON 원문 확보 후 추가 |

### 4.6 YOLO 형식으로 변환

```bash
python3 yolo/dataset_gen/convert_to_yolo.py yolo/datasets/sim_raw/wide_000  yolo/datasets/turtle_ninja --split train
python3 yolo/dataset_gen/convert_to_yolo.py yolo/datasets/sim_raw/wrist_000 yolo/datasets/turtle_ninja --split train
```

- 퍽 라벨은 sim에서 모양까지 구분해서(`puck_cyl`, `puck_box`, `*_fallen`) 저장해 두고, 변환할 때 `--classes`로 묶을지 정한다.
  - `--classes merged` (기본): `qr, puck, puck_fallen, signal_tower`
  - `--classes shape`: `qr, puck_cyl, puck_box, puck_cyl_fallen, puck_box_fallen, signal_tower`
  - 모양 구분 여부가 바뀌면 데이터를 다시 만들 필요 없이 변환만 다시 한다. `[확인 필요: 모양 구분 여부]`
- 4px보다 작은 박스는 학습 노이즈라서 제외한다.
- 처음 변환할 때 `data.yaml`이 생성된다. 실제 데이터 검증셋 경로(`images/val_real`)는 실제 데이터를 넣은 뒤 확인한다.

## 5. 학습 (개발 PC, RTX 5060 8GB)

### 환경 주의사항

- **YOLO 학습용 venv는 Isaac Sim venv와 따로 만든다.** Isaac Sim venv에 ultralytics를 설치하면 NumPy·OpenCV·PyTorch 버전이 바뀌어서 Isaac Sim이 깨질 수 있다.
- RTX 50 시리즈(Blackwell)는 **CUDA 12.8 이상으로 빌드된 PyTorch**가 있어야 한다. 예전 cu118/cu121 휠을 쓰면 GPU를 인식하지 못하거나 커널 오류가 난다.

```bash
python3.12 -m venv ~/pa-course/.venv-yolo
source ~/pa-course/.venv-yolo/bin/activate
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu128
pip install ultralytics
```

### 데이터셋 구성

```
yolo/datasets/turtle_ninja/
  images/{train,val_sim,val_real,test_real}/
  labels/{train,val_sim,val_real,test_real}/
  data.yaml
```

- `val_real`과 `test_real`은 **실제 영상으로만** 만든다. 모델 선택과 경량화 판단은 모두 이 셋을 기준으로 한다.
- 데이터셋과 가중치는 커밋하지 않는다 (README 규칙).

### 2단계 학습

```bash
# 1단계: 합성 데이터로 사전 학습
yolo detect train model=yolo26n.pt data=data_sim.yaml imgsz=1280 rect=False \
  epochs=150 batch=8 hsv_h=0.3 hsv_s=0.5 hsv_v=0.4 mosaic=1.0 close_mosaic=15 \
  project=runs/wide name=sim_pre

# 2단계: 합성 + 실제 데이터를 섞어 fine-tune (실제 데이터는 반복 샘플링으로 비중을 30% 정도로)
yolo detect train model=runs/wide/sim_pre/weights/best.pt data=data_mix.yaml imgsz=1280 \
  epochs=60 batch=8 lr0=0.002 project=runs/wide name=mix_ft
```

- 데이터에는 광각(1280×720)과 손목(640×480) 이미지가 섞여 있다. 학습 때는 긴 변을 `imgsz`에 맞춰 리사이즈하므로 손목 이미지는 2배로 확대되어 들어간다. 반면 손목 엔진(480×640)은 원본 크기 그대로 추론하므로, 학습 때보다 객체가 절반 크기로 보인다. 손목에서는 퍽이 충분히 크게 보이고(0.3m에서 약 50px) `scale=0.5` 증강이 이 차이를 덮어 준다. `val_real`에서 손목 이미지 성능이 낮게 나오면 손목 이미지만 모아 `imgsz=640`으로 짧게 추가 fine-tune한다.

- 8GB VRAM에서 입력 1280은 batch 8 정도가 한계다. OOM이 나면 `batch=-1`(자동)을 쓴다.
- 색에 따라 나뉘는 클래스가 없으므로(퍽 색, 신호등 상태 모두 후처리) `hsv_h`를 0.3 정도로 크게 줘서 탐지기가 색에 둔감하도록 만든다.
- `fliplr`은 기본값을 그대로 둔다 (QR은 위치 탐지만 하므로 좌우 반전해도 문제없음).

## 6. 경량화 (Jetson Orin Nano)

### 원칙

- **TensorRT 엔진은 반드시 Jetson에서 직접 빌드한다.** 다른 GPU에서 만든 엔진은 Jetson에서 실행되지 않는다. PC에서는 `.pt`(또는 ONNX)까지만 만든다.
- 정확도는 `val_real`, 속도는 SLAM·Nav2를 함께 띄운 상태에서 측정한다.

### Jetson 준비

```bash
sudo nvpmodel -m 0        # 최대 성능 모드 (JetPack 버전에 따라 MAXN SUPER)
sudo jetson_clocks
```

### 실험 순서

| 단계 | 방법 | 명령 | 기대 효과 |
|---|---|---|---|
| 0 | PyTorch 기준선 | – | 비교 기준 |
| 1 | TensorRT FP16 | 아래 코드 (`half=True`) | 속도 크게 향상, 정확도 손실 거의 없음. **기본 채택** |
| 2 | TensorRT INT8 PTQ | 아래 코드 (`int8=True`) | FP16보다 추가로 빨라짐. 작은 물체 정확도가 떨어질 수 있음 |
| 3 | 입력 줄이기 | ROI crop, 광각 544×960 | 연산량이 거의 입력 픽셀 수에 비례해 줄어듦 |
| 4 | (선택) QAT | INT8 손실이 클 때만 | 시간이 많이 들어서 일정상 후순위 |

같은 `best.pt`에서 카메라별로 입력 크기만 다른 엔진 2개를 만든다 (Jetson에서 실행).

```python
from ultralytics import YOLO

m = YOLO("best.pt")
m.export(format="engine", imgsz=(736, 1280), half=True)   # 광각 (h, w) → 이름을 wide_736x1280.engine으로 변경
m.export(format="engine", imgsz=(480, 640), half=True)    # 손목      → wrist_480x640.engine
# INT8: half=True 대신 int8=True, data="calib_real.yaml" (캘리브레이션은 카메라별 실제 영상으로)
```

- INT8 캘리브레이션 데이터(`calib_real.yaml`)는 **실제 영상**으로 300~500장 준비한다. 합성 영상으로 캘리브레이션하면 실제 영상의 activation 분포와 어긋나서 손실이 커진다.
- pruning이나 distillation은 일정(11/11 시연)을 고려해 하지 않는다.
- YOLO26은 NMS가 필요 없는 end-to-end 구조라서 후처리 시간이 줄고, 지연 시간도 일정하게 나온다.

| wrist | FP16 | 480×640 | | | | |
| wrist | INT8 | 480×640 | | | | |
| wide + wrist 동시 로드 | FP16 | – | – | – | – | |

**채택 기준(제안)**: INT8의 mAP 손실이 FP16 대비 1.5%p 이하이고 퍽 recall 손실이 2%p 이하일 때만 INT8을 쓴다.

### ROS 2 노드 구성

```
[yolo_detector]  ← 한 프로세스에서 엔진 2개 로드 (CUDA context 1개)
  /wide_cam/image_raw        → /perception/wide/detections   (vision_msgs/Detection2DArray)
                             → /perception/pucks_floor        (homography 적용, base_link 기준)
  /wrist_cam/color + depth   → /perception/wrist/pucks        (depth 마스크 → 3D 위치, 색, 서 있음/넘어짐)
                               (손목 쪽은 상태 머신이 enable 서비스로 켜고 끔)
[qr_decoder]
  /wrist_cam/color           → /perception/qr_task            (검증을 통과한 JSON)
```

- 처음에는 Ultralytics Python API로 `.engine`을 직접 불러 쓰는 rclpy 노드로 시작한다. 지연이 문제가 되면 C++ TensorRT 노드로 옮긴다.
- 이미지 복사를 줄이기 위해 광각은 필요한 해상도로 미리 받는다 (카메라 드라이버 설정).

## 7. sim-to-real 개선

### 7.1 학습 전 (gap 줄이기)

1. **카메라 일치**: 4.2절. intrinsics, 왜곡, 해상도, 장착 위치를 실물과 맞춘다.
2. **노출과 화이트밸런스 고정**: 실제 카메라의 자동 보정이 sim과 가장 크게 어긋나는 부분이다.
3. **실측 기반 랜덤화**: 퍽 색과 조명 범위를 실제 측정값 주변으로 잡는다. 무작위 범위를 너무 넓게 잡으면 오히려 실제 성능이 떨어진다.
4. **실제 텍스처 사용**: 11/4 맵 공개 직후 바닥과 벽을 촬영해 sim 텍스처를 교체하고 데이터를 다시 생성한다.

### 7.2 학습 (gap 메우기)

1. 실제 데이터를 일찍 모은다. 로봇을 수동으로 몰며 rosbag을 녹화하고 프레임을 추출한다.
2. sim 모델로 자동 라벨링 → 사람이 수정. 이렇게 하면 라벨링 시간이 크게 줄어든다.
3. 목표: 실제 데이터 학습용 300~500장 + `val_real` 150장 + `test_real` 100장.
4. sim 검증셋과 실제 검증셋의 mAP 차이를 계속 기록한다. 차이가 줄지 않는 클래스나 시점을 찾아 그 부분 데이터를 보강한다.

### 7.3 추론 단계 (모델 밖에서 오탐 걸러내기)

| 방법 | 내용 |
|---|---|
| 시간 필터 | 최근 N 프레임 중 M번 이상 탐지될 때만 확정 (예: 5중 3) |
| 크기 검증 (손목) | depth와 bbox 크기로 실제 크기를 계산해서 3×3×6cm에서 크게 벗어나면 버림 |
| 바닥 평면 검증 (광각) | 퍽 bbox 하단이 바닥 평면 위에 있어야 함. 벽 위에 뜬 퍽은 오탐 |
| 맵 검증 | homography로 구한 좌표가 벽 안쪽이나 맵 밖이면 버림 |
| 색 신뢰도 | 판별에 쓴 유효 픽셀 수가 적거나 hue 분산이 크면 "모름"으로 처리하고 더 가까이 가서 다시 봄 |
| 연결 부품 위치 검증 | 연결 부품 83개의 위치는 맵에서 고정(격자 x=-2.202+0.367i, y=-3.152+0.394j)이다. SLAM 위치로 파란 퍽 후보의 맵 좌표를 구해서 연결 부품 중심에서 5cm 안이면 버림. 선반이 없는 곳의 바닥 높이(0~3cm)·꼭대기(36~39cm)는 특히 의심 |

### 7.4 QR 디코딩 안정화

- 손목 카메라로 정면(±15° 이내), 0.3~0.5m 거리에서 읽는다.
- 전처리를 단계적으로 시도한다: 원본 → CLAHE → 샤프닝 → 이진화. 하나라도 성공하면 채택한다.
- 여러 프레임에서 같은 문자열이 나와야 확정한다.
- JSON 파싱 후 스키마를 검증한다(필수 키, 색 값이 R/G/B 중 하나인지, 좌표 범위). 실패하면 재시도한다.

## 8. 적재함 운용

적재함은 칸이 나뉘어 있고 광각에서는 일부만 보이므로, **비전보다 상태 기록을 먼저 믿는 구조**로 만든다.

1. 퍽을 넣을 때 `inventory = {slot_id: color}`를 기록한다.
2. 적재함 확인용 팔 자세를 하나로 고정하고, 그 자세에서 각 칸의 이미지 ROI를 미리 저장해 둔다.
3. 꺼내기 전에 손목 카메라로 칸마다 확인한다.
   - 비었는지 / 차 있는지: ROI 안의 depth 높이로 판단
   - 색: ROI 내부 HSV 판별 (2절과 같은 방법)
4. 기록과 비전 결과가 다르면 그 칸만 YOLO + depth 마스크로 다시 확인하고, 그래도 다르면 비전 결과를 따르고 기록을 갱신한다.

이렇게 하면 적재함 단계에서는 YOLO 없이도 대부분 동작하고, YOLO는 불일치를 해결하는 보조 수단이 된다.

## 11. 측정 절차

### 준비물

버니어캘리퍼스, 줄자, 체커보드 인쇄물(A4 또는 A3), 흰 A4 종이, 휴대폰 각도계·조도계 앱, 전자저울, 카메라 2대가 연결된 로봇(또는 Jetson)

결과는 모두 `config/` 아래 yaml로 저장하고, 원본 사진은 팀 공유 드라이브에 둔다 (레포에 커밋하지 않음).

### 11.1 카메라 캡처 모드

FPS는 우리가 정하는 값이지만, **요청한 값이 그대로 나온다는 보장은 없다.** 아래 제약 안에서 고르고, 실제로 나오는지 측정해서 확정한다.

| 제약 | 내용 |
|---|---|
| 카메라 지원 조합 | 해상도·포맷·FPS는 정해진 조합만 지원한다. 예를 들어 YUYV 1920×1080은 5fps만 되고, MJPG로 해야 30fps가 되는 식 |
| USB 대역폭 | 두 카메라가 같은 USB 컨트롤러를 쓰면 대역폭이 모자라서 FPS가 떨어지거나 프레임이 끊긴다 |
| Jetson 부하 | MJPG는 디코딩에 CPU가 든다. SLAM·Nav2와 함께 돌릴 때 따라오는지 확인 |
| 노출 시간 | 노출 시간은 프레임 간격보다 길 수 없다 (30fps → 최대 33ms). 어두운 곳에서 노출을 길게 잡으면 FPS가 같이 떨어짐 |
| 필요한 처리 속도 | YOLO는 10~15Hz로 돌리므로 카메라를 그보다 훨씬 빠르게 받아도 버려지는 프레임만 늘어난다 |

```bash
v4l2-ctl -d /dev/video0 --list-formats-ext     # 지원 해상도·포맷·FPS 조합
lsusb -t                                       # 두 카메라가 같은 컨트롤러(Bus)에 있는지
ros2 topic hz /wide_cam/image_raw              # 실제로 나오는 FPS (두 카메라 동시에 켠 상태로)
```

- 광각: 1280×720 MJPG 30fps부터 시험해 본다. SLAM·Nav2와 함께 15fps 이상 안정적으로 나오는 가장 높은 해상도로 정한다.
- D435 컬러: 640×480 30fps (depth도 같은 FPS로 맞춰 정렬).
- **한 번 정한 해상도는 바꾸지 않는다.** 해상도가 바뀌면 캘리브레이션, sim 렌더 설정, 엔진 입력 크기를 모두 다시 해야 한다. FPS는 나중에 바꿔도 된다.

### 11.2 노출·화이트밸런스·전원 주파수 고정

```bash
v4l2-ctl -d /dev/video0 --list-ctrls           # 컨트롤 이름 확인 (커널마다 다름)
```

1. 자동 노출, 자동 화이트밸런스, 자동 초점(있다면)을 끈다.
2. 전원 주파수를 60Hz로 설정한다 (`power_line_frequency=2`, RealSense는 `rgb_camera.power_line_frequency`). 한국 전원은 60Hz라서 조명이 1초에 120번 깜빡인다. 노출 시간을 **1/120초(8.3ms)의 배수**로 두지 않으면 화면에 줄무늬가 생기고 프레임마다 밝기가 출렁인다.
3. 노출 값은 2.1절의 방법으로, 신호등을 켜고 퍽과 같이 화면에 넣은 상태에서 정한다.
4. 확정한 값을 `config/camera_wide.yaml`, `config/camera_wrist.yaml`에 저장한다.

### 11.3 내부 파라미터 캘리브레이션

**Arducam (광각): 직접 캘리브레이션**

1. 체커보드를 인쇄한다. 내부 코너 9×6, 칸 25mm를 권장한다.
2. **인쇄된 칸 크기를 캘리퍼스로 실측한다.** 프린터가 크기를 조금씩 바꾸므로 8칸 길이를 재서 8로 나눈 값을 쓴다.
3. 인쇄물을 휘지 않는 판(폼보드, 아크릴)에 평평하게 붙인다.
4. 11.1에서 확정한 캡처 모드, 11.2의 고정 노출로 30~50장을 찍는다.
   - 화면 **가장자리와 모서리**에 보드가 오는 사진을 많이 넣는다 (광각 왜곡은 가장자리에서 가장 큼).
   - 보드를 앞뒤, 좌우로 30~45°씩 기울인 사진을 섞는다.
   - 거리를 가까이부터 멀리까지 다양하게 한다.
   - 흔들린 사진은 뺀다 (노출이 길면 삼각대나 거치대 사용).
5. OpenCV **fisheye 모델**(`cv2.fisheye.calibrate`)로 계산한다.
6. **재투영 오차 0.5px 이하**면 합격이다. 넘으면 오차가 큰 사진을 빼고 다시 계산한다.
7. K, D, 해상도를 `config/camera_wide.yaml`에 저장한다. 이 값을 Isaac Sim fisheye 카메라에 그대로 넣는다.

**D435 (손목): 공장 값 사용**

```bash
ros2 topic echo /camera/camera/color/camera_info --once
```

해상도마다 값이 다르므로 **최종 해상도에서** 뽑는다. depth는 color에 정렬(`align_depth.enable: true`)해서 쓰므로 color 쪽 값만 있으면 된다.

### 11.4 카메라 장착 위치 (외부 파라미터)

| 항목 | 1차 측정 (빠름) | 최종 측정 (정확) |
|---|---|---|
| 광각 높이 | 줄자: 바닥 → 렌즈 중심 | 아래 체커보드 방법 |
| 광각 기울기 | 카메라 뒷면 평평한 곳에 휴대폰 각도계 앱 | 아래 체커보드 방법 |
| 광각의 `base_link` 기준 위치 | 줄자: 로봇 회전 중심 → 렌즈 (x, y, z) | URDF/CAD 값 |
| D435의 손목 기준 위치 | 캘리퍼스: 마지막 링크 기준 오프셋 | 마운트 CAD 값 |

**최종 측정 방법 (광각)**: 체커보드를 바닥에 평평하게 놓고 로봇 기준 위치(예: 로봇 정면 0.6m, 좌우 중앙)를 줄자로 정확히 맞춘다. 사진 한 장을 찍어 `cv2.solvePnP`(fisheye는 코너를 먼저 undistort)로 계산하면 카메라 높이와 기울기가 나온다. 같은 데이터로 **바닥 homography**(픽셀 → 바닥 좌표)도 얻는다. 보드 위치를 2~3군데 바꿔 측정해서 결과가 일치하는지 확인한다.

### 11.6 신호등

**식별된 제품**: 한영넉스(Hanyoung NUX) **STL040 시리즈** LED 사인타워, Ø40 원주형. 내부 기판에 `STL040-F…` 각인이 있다.

| 형명 코드 `STL040-□-□□□-□-□` | 의미 |
|---|---|
| 기능 `A` / `F` | A: 점등 전용 / F: 점등·점멸·부저 (외부 신호로 선택) |
| 전원 `C51` / `A11` | 24V AC/DC / 100~240V AC |
| 단수 `3` | 3단 (R, Y, G) |
| 설치 `D` / `L` / `M` | 직접 설치(볼트 고정) / L형 지지대 / 플라스틱 지지대 |

- 사진상 바닥에 볼트가 나와 있으므로 **직접 설치형(D)**으로 보인다. 정확한 형명은 본체나 박스의 라벨로 확인한다.
- 매뉴얼 높이 표에서 계산한 1단 간격(약 41mm)은 실측한 렌즈 높이(32mm)와 다르다. 표에는 설치부와 결합부가 포함된 것으로 보이며, **모델링에는 아래 실측값을 쓴다.**
- **실측 치수** (지름 40mm, 받침 없음. 맨 아래가 초록 렌즈):

| 부위 (위→아래) | 높이 | 위치 (위에서부터) | 본체 내 비율 |
|---|---|---|---|
| 회색 캡 | 12mm | 0~12 | 0.00~0.10 |
| 빨강 칸 (구분선 1mm + 렌즈 35mm) | 36mm | 12~48 | 0.10~0.40 |
| 노랑 칸 (구분선 1mm + 렌즈 35mm) | 36mm | 48~84 | 0.40~0.70 |
| 초록 칸 (구분선 1mm + 렌즈 35mm) | 36mm | 84~120 | 0.70~1.00 |
| **합계** | **120mm** (실측 전체 121mm) | | |

  칸 높이 36mm에 검은 구분선 1mm가 포함된 것으로 계산했다. 이렇게 하면 합계가 실측 전체 높이와 1mm 이내로 맞고, 사진의 픽셀 비율과도 일치한다.
- 점등 판별 비율(`TIERS`)은 실제 카메라로 찍은 bbox에서 최종 보정한다.
- Isaac Sim 모델: 원통 7개(캡 1, 구분선 3, 렌즈 3)를 위 치수대로 쌓는다. 구분선은 검은 무광 재질로 만든다.
- **내부(LED 기판)와 렌즈 두께는 모델링하지 않는다.** 렌즈를 속이 빈 반투명 원통으로 만들면 실시간 RTX 렌더링에서 투과 표현이 부정확하고 데이터 생성 속도만 느려진다. 1~2m 거리에서는 지름 40mm 물체의 내부 구조가 거의 보이지 않으므로, 속이 찬 원통에 재질로 겉모습만 맞춘다.
  - 꺼진 칸: 해당 색 OmniPBR, 약간 어둡게, roughness 0.3~0.5 (세로 골무늬 반사 대신)
  - 켜진 칸: 같은 색 emissive. 세기는 실제 카메라 사진과 비교해서 맞추고 ±50% 랜덤화
  - 꺼진 칸 밝기도 ±30% 랜덤화 (주변 조명이 렌즈를 통과해 내부가 비치는 정도가 장소마다 다름)
  - 실제 카메라로 찍은 꺼짐·R·Y·G 사진과 sim 렌더를 나란히 놓고 비교해서 맞춘다
- 기능이 `F`라면 점멸 모드가 있으므로, 점등 판별에서 점멸 주기(매뉴얼 기준 분당 60회)보다 긴 구간으로 다수결을 해야 한다.


| 항목 | 방법 |
|---|---|
| 지름 | 캘리퍼스로 렌즈 부분 측정 (캡 지름이 다르면 따로) |
| 칸별 높이 | 위에서부터 캡, 빨강, 노랑, 초록 순서로 캘리퍼스 측정 → 2절 `TIERS` 비율에 반영 |
| 설치 방식과 높이 | 바닥에 세우는지, 벽·거치대에 다는지 / 바닥에서 신호등 하단까지 높이 |
| 동작 방식 | 한 번에 한 칸만 켜지는지, 깜빡이는지, 상태 전환 주기 |
| 점등 사진 | 로봇 카메라 2대(11.2의 고정 노출)로 꺼짐·빨강·노랑·초록 4가지 상태를 1m, 2m 거리에서 촬영 |

### 11.7 QR

| 항목 | 방법 |
|---|---|
| 크기 | 검은 사각형 바깥 한 변 (흰 여백 제외) |
| 흰 여백(quiet zone) | QR 테두리 → 종이 끝 |
| 붙이는 높이 | 바닥 → QR 중심 |
| 재질 | 일반 종이 / 코팅. 코팅이면 조명 반사로 디코딩이 실패할 수 있으니 비스듬한 각도 사진도 찍어 둔다 |
| **JSON 원문** | 실제 문제 QR 하나를 휴대폰으로 읽어 원문 그대로 복사 |

JSON 원문으로 QR 버전(칸 수)을 계산해서 손목 카메라의 디코딩 거리를 정하고, 디코더의 스키마 검증 코드를 작성한다.

### 11.9 색 기준값 (로봇 카메라로)

11.2의 노출 고정이 끝난 뒤에 측정한다.

1. 시연장과 비슷한 조명에서 퍽 R/G/B, **파란 벽 연결 부품**, 흰 A4 종이를 같이 놓는다. 파란 퍽과 연결 부품의 hue 차이가 있는지 확인한다 (차이가 확실하면 색 판별에서도 걸러낼 수 있음).
2. 광각(0.8m, 1.2m)과 D435(0.3m)로 각각 찍는다.
3. 퍽을 돌려 가며 밝은 면과 그림자 면이 모두 나오게 여러 장 찍는다.
4. 각 퍽 영역의 HSV 중앙값과 분포를 뽑는다.

```python
import cv2, numpy as np
img = cv2.imread("wide_rgb_puck.png")
x, y, w, h = cv2.selectROI("roi", img)            # 마우스로 퍽 영역 드래그
hsv = cv2.cvtColor(img[y:y+h, x:x+w], cv2.COLOR_BGR2HSV).reshape(-1, 3)
print("median H,S,V:", np.median(hsv, 0), " H p10/p90:", np.percentile(hsv[:, 0], [10, 90]))
```

5. 흰 종이 영역의 RGB도 기록한다. 시연장에서 색이 틀어졌는지 확인하는 기준이 된다.
6. 결과를 `config/color_wide.yaml`, `config/color_wrist.yaml`에 저장한다. 이 값을 Isaac Sim 퍽 머티리얼 색의 중심값으로도 쓴다.
